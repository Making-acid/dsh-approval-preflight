# 授权模型：计算图 + 语义节点 + 节点级一次性授权

> 状态：**结构已确认**（2026-10-26 原型评审通过；实现待排期）
> 取代：`docs/grant-model-v1.1.md`（已删除）与 `docs/design.md` 第 3–6 节中「按权限类别批量授权」的部分。
> 保留：右侧面板、超时让路、从会话日志回放、模型不能自我授权。

## 评审结论（2026-10-26）

- 模型结构（计算图 → 语义节点 → 节点级一次性授权 → 审计痕迹）确认通过，不再调整。
- 交互形态以 `docs/prototype/grant-panel.html` 定稿：顶部计算图概览（状态色 + 待批徽标 + 点击跳转）、节点卡（动作 / 来源 / 目标 + 补充说明 + 影响标签 + 依赖）、卡内展开审计、底部一键批准。
- 采用默认取舍：同一时刻只允许一个 running 节点；节点失败不消耗额度、可直接重试；审计在节点卡内展开；影响类型先按四类（写文件 / 删除 / 执行 / 网络），其中「删除」暂按命令执行（`exec`）归类。
- 第 15 节的开放问题按以上默认值执行；实现评审时如有不同意见再调整。


## 1. 一句话

模型先给出**计算图**（要做哪些事、数据怎么流动），再在图上标出**会对外部世界产生影响的节点**（下载什么到哪里、写什么、删什么、执行什么），用户**逐节点批准**；执行时模型声明「进入/结束某个节点」，插件只在该节点声明的影响范围内放行，并在事后留下**实际执行痕迹**供审计。

## 2. 上一版错在哪

| 版本 | 授权单位 | 错在哪 |
| --- | --- | --- |
| 1.0 | 权限类别（fs-write / exec / network / danger） | 点一次 = 本会话同类操作永久免审，权限面被悄悄放大 |
| 1.1 草案 | 具体命令 / 绝对路径（argv 前缀、路径相等） | 把「本质」落成了代码级比对。用户批准的是「下载 better-sqlite3 到项目依赖」，实际命令可能是 `pnpm add`，也可能是改 `package.json` 手写——代码层比对既不成立也不该成立 |
| **本版** | **计算图上的语义节点** | 批准的是「这件事」，命令与代码是实现细节 |

## 3. 三层模型

```
第一层  计算图       要做什么：节点 + 数据依赖（不涉及权限）
          ↓ 由模型推导
第二层  权限节点     图上哪些节点会碰外部世界，各自「本质」是什么（动作 + 来源 + 目标）
          ↓ 用户逐节点批准
第三层  执行绑定     模型声明进入/结束某节点；插件在该节点影响范围内放行；事后留痕
```

**插件不判断命令对不对**，它只判断：这个调用是否落在「你批准过的那个节点正在运行 + 该节点声明的影响类型」之内。

## 4. 计算图数据模型

```jsonc
{
  "goal": "给项目加 SQLite 支持并跑通构建",
  "version": 1,
  "nodes": [
    {
      "id": "N1",
      "title": "读现有依赖清单",
      "effect": "read",                    // 无外部影响
      "dependsOn": []
    },
    {
      "id": "N2",
      "title": "下载 better-sqlite3 并写入项目依赖",
      "effect": "download",
      "essence": {                          // 结构化：用户看这个
        "action": "download",
        "source": "npm registry · better-sqlite3",
        "target": "项目依赖目录（node_modules/ 与 package.json）",
        "details": "把 better-sqlite3 安装为运行时依赖"
      },
      "note": "不关心用 pnpm 还是 npm，也不关心是否手写 package.json",
      "dependsOn": ["N1"],
      "impacts": ["network", "fs-write"],   // 预计会触发的影响
      "escalate": false,
      "permission": "required"              // required | none
    },
    {
      "id": "N3",
      "title": "新建数据库封装",
      "effect": "write",
      "essence": {
        "action": "write",
        "target": "src/db.ts（工作区内）",
        "details": "新增一个数据库连接与查询封装文件"
      },
      "impacts": ["fs-write"],
      "dependsOn": ["N2"],
      "permission": "required"
    },
    {
      "id": "N4",
      "title": "跑构建",
      "effect": "execute",
      "essence": {
        "action": "execute",
        "target": "工作区构建脚本（产物写入 dist/）",
        "details": "执行项目构建，确认类型与打包都通过"
      },
      "impacts": ["exec", "fs-write"],
      "dependsOn": ["N3"],
      "permission": "required"
    }
  ]
}
```

### 4.1 字段

| 字段 | 说明 |
| --- | --- |
| `id` | 节点短标识，稳定不变，用于批准与审计对账 |
| `title` | 一句话标题，面板显示 |
| `effect` | `read` / `compute` / `download` / `write` / `delete` / `execute` / `network` |
| `essence` | **结构化本质**：`action` + `source?` + `target?` + `details` |
| `note` | **自由补充**：模型解释意图、边界、为什么不需要更精确 |
| `impacts` | 预计触发的影响类型：`fs-write` / `exec` / `network` / `fs-delete` |
| `escalate` | 是否需要提权（danger-full-access）才能完成 |
| `permission` | `required` = 用户必须批准；`none` = 只展示不拦 |
| `dependsOn` | 计算图的数据/顺序依赖：决定就绪判定，也决定被挡住时哪些节点是可切换的独立分支 |

## 5. 节点状态机

```
proposed ──用户批准──▶ approved ──模型声明开始──▶ running ──结束(成功)──▶ done（权限已消耗）
   │                     │                        │
   │                     │                        ├──结束(失败)──▶ approved（不消耗，可重试）
   │                     │                        └──审批超时/空闲超时──▶ suspended（不消耗，可继续）
   │                     ├──用户撤销──▶ revoked
   │                     └──图被整体重写──▶ stale
   └──用户拒绝──▶ rejected

suspended ──preflight_node_start──▶ running（保留原批准，不需要重新批准）
suspended ──用户撤销──▶ revoked
```

- 同一时刻**只允许一个 running 节点**（启动第二个需先结束当前），保证审计归属干净。
- `running` 超过 `nodeIdleSeconds`（默认 600s）自动挂起（`suspended`），不消耗权限。
- **挡住审批时自动挂起**：`running` 节点遇到未申报的调用，`approvalTimeoutSeconds` 内没等到用户回答 → 自动转 `suspended`，释放执行槽位，并把「不依赖它的可做节点」交给模型（见 §7.3）。
- `preflight_graph` 整体重写 → 所有旧节点变 `stale`，需重新批准；追加接口不影响已有批准。

## 6. 用户交互（面板）

```
┌ 任务与权限预检                                         × ┐
│ 目标：给项目加 SQLite 支持并跑通构建                       │
│ 2 个待批准 · 1 个已批准 · 1 个执行中                       │
│                                                          │
│ N1 读现有依赖清单                      无外部影响   只读   │
│                                                          │
│ ▾ N2 下载 better-sqlite3 并写入项目依赖                    │
│    下载 · 来源 npm registry · 目标 项目依赖目录            │
│    影响：网络 + 写文件                                     │
│    [批准]  [拒绝]                                          │
│                                                          │
│ ▸ N3 新建数据库封装         已批准 · 待执行                │
│ ▸ N4 跑构建                 待批准                         │
│                                                          │
│ [批准全部待批准]                Esc 关闭          [刷新]   │
└──────────────────────────────────────────────────────────┘
```

- 按依赖顺序排列；`dependsOn` 以缩进/连线体现。
- 每行展示：本质（结构化）、影响标签、提权标记、状态、操作。
- 已批准/已完成节点可展开，查看**审计痕迹**（实际执行了什么）。
- 长图可滚动；默认展开待批准节点。
- 文案明确：批准的是「这件事」，不是某条具体命令。

## 7. 运行时绑定与放行

### 7.1 模型声明节点边界

模型侧工具：

| 工具 | 作用 |
| --- | --- |
| `preflight_graph` | 提交/替换计算图（含权限节点申报） |
| `preflight_graph_append` | 往图里**追加**节点（不适合作废已有批准） |
| `preflight_node_start` | 声明「开始执行 N2」 |
| `preflight_node_end` | 声明「N2 结束，成功/失败」 |
| `preflight_status` | 查看节点状态、待批准项、当前 running 节点 |

授权动作**只能由用户在面板完成**，模型没有任何工具能批准节点。

### 7.2 放行判定

审批请求（`approval/request`，`{prepend:true}`）到达时：

```
1. 取当前 running 节点 N
2. 无 running 节点 → 交给原生审批卡
3. 把 toolName 映射成影响类型：
     write / edit            → fs-write
     pwsh / bash             → exec
     web_fetch / web_search  → network
     其它（MCP / terminal_*）→ 不可映射
4. 该影响类型在 N.impacts 内，且（若调用要求提权）N.escalate == true
     → 返回 allowed-once，同时把这次调用记入 N 的审计列表
   否则 → 交回原生审批卡（可归类时同时启动超时让路）
```

### 7.3 超时挂起与独立分支切换

`dependsOn` 不只是展示用的顺序，它决定「被挡住时还能做什么」：

```
运行中的节点 N
  └─ 遇到未申报的调用（影响类型不在 N 的申报里）
       ├─ 用户回答「允许」→ 该调用放行（一次性，不产生节点批准）
       └─ approvalTimeoutSeconds 内没回答
            ├─ 自动挂起 N：status = suspended，running = null，批准保留
            ├─ 计算独立分支：① 已批准 ② 依赖闭包不含 N ③ 依赖全部 done
            └─ agent.inject() 告诉模型：
                 「与 N 无依赖、现在能做：M、K。下一步 preflight_node_start M；
                   N 可稍后 preflight_node_start 继续（不需要重新批准）；
                   需要那个操作就 append 一个新节点并请用户批准。」
```

- **为什么只挑独立分支**：执行槽位只有一个；`M` 若依赖 `N`（直接或传递），`N` 没完成时 `M` 的依赖条件不成立，切过去也做不了。所以候选集 = `approved ∧ ready ∧ closure(M) ∌ N`。
- **没有任何候选时**：明确告诉模型「剩余工作都依赖 N，没有可切换的独立分支」，不要重试；同时把还在等批准的独立节点列出来，让用户知道批准后就能继续。
- **不改授权**：挂起只释放槽位，不产生新批准；切换目标必须是用户已经批准过的节点。用户没批准的部分只会被「列出来提醒」，不会被自动开始。
- **可恢复**：挂起是插件自己的限制，不是失败；`preflight_node_start N` 直接续跑，批准仍然有效（一次性授权只在该节点**成功结束**时消耗）。
- 超时让路发生在「有 running 节点」时；没有 running 节点时审批仍走原生卡（插件不替用户撤回一个它没有上下文可切换的请求）。

## 8. 审计痕迹

每个节点维护一份审计列表，记录**运行期间实际发生的调用**：

```jsonc
{
  "nodeId": "N2",
  "audit": [
    { "at": 1761480000000, "tool": "web_fetch", "summary": "GET registry.npmjs.org/better-sqlite3", "outcome": "ok" },
    { "at": 1761480001200, "tool": "write", "summary": "package.json", "outcome": "ok" },
    { "at": 1761480004000, "tool": "pwsh", "summary": "pnpm add better-sqlite3", "outcome": "ok" }
  ]
}
```

- 面板里展开节点即可看到「N2 实际执行了什么」，与批准的「本质」对照。
- 审计是**事后核对**，不阻断执行；这是对「语义不可验证」的补偿手段。
- 审计数据来自会话日志的 `tool/call` + `tool/result`，按 running 区间归属，可回放重建。

## 9. 持久化与回放

| 事实 | 日志来源 |
| --- | --- |
| 计算图 | `tool/call`：`preflight_graph` / `preflight_graph_append` |
| 节点批准 | 注入的用户消息标记 `[[preflight:approve:<graphVersion>:<nodeId>]]` |
| 节点挂起 | 注入的用户消息标记 `[[preflight:suspend:<graphVersion>:<nodeId>]]` |
| 节点执行区间 | `tool/call`：`preflight_node_start` / `preflight_node_end`（`suspended` 后再 start 即续跑） |
| 审计 | `tool/call` + `tool/result`，按执行区间归属 |

回放规则：按 seq 顺序重建图与节点状态；区间外的调用不归属任何节点；遇到无法解释的事件（缺 start、节点 id 未知、版本不匹配）→ 该节点置 `stale` 并要求重新批准（**fail-closed**：宁可多问，不可多放）。

| 保留 | 替换 |
| --- | --- |

| 模型不能自我授权 | 新增：节点边界声明与审计痕迹 |

## 11. 安全与信任边界（必须说清）

- **能防住的**：永久性类别放行（不存在了）；未申报的影响类型（永远弹原生卡）；模型自我授权（没有这种工具）；重启后额度被重置放大（回放 + fail-closed）。
- **防不住的**：模型在某个已批准节点内做了与该节点语义不符、但影响类型相同的事（例如批准「下载 better-sqlite3」，它下载了别的包）。这类偏差只能靠**审计痕迹**发现，不能靠拦截。
- **为什么可以接受**：这个插件的目标是「减少审批延迟、同时让用户知道自己批准了什么」，不是沙箱。真正的隔离仍由 Harness 的沙箱与权限模式负责。
- **建议配套**：高风险节点（删除、提权、生产环境）模型应在 `note` 里写清楚，用户可要求更具体的节点再批准。

## 12. 配置

```yaml
approvalTimeoutSeconds: 90     # 0 = 关闭让路
nodeIdleSeconds: 600           # running 节点超时自动结束（不消耗权限）
maxNodes: 80                   # 单张计算图的节点上限
wakeOnGrant: true
```

## 13. 测试计划

1. **图校验**：节点 id 唯一、`dependsOn` 不悬空、`impacts` 合法、`escalate` 与影响类型一致。
2. **状态机**：批准 → 开始 → 成功（消耗）/ 失败（不消耗可重试）/ 超时自动结束 / 撤销 / 整体重写作废。
3. **放行判定**：running 节点 + 影响类型命中 → allowed-once 并记审计；类型超出 → 交回；无 running → 交回；提权未申报 → 交回。
4. **并发限制**：running 期间再 start 另一个节点被拒绝。
5. **回放**：完整/异常事件序列下重建图与节点状态；异常序列 fail-closed。
6. **审计**：调用归属正确、区间外调用不归属、面板可渲染。
7. **面板**：节点行、影响标签、状态、展开审计（离线 DOM 测试）。
8. **契约测试**：假 Cordis 上下文验证审批监听、图工具、面板通道。

## 14. 明确不做（本版）

- 不验证命令与代码是否语义一致（做不到，只留审计）。
- 不做目录/命令通配规则引擎（不需要：放行按节点 + 影响类型）。
- 不自动放行 `terminal_*`（无法界定一次调用边界）与不可映射的 MCP 工具。
- 不接管原生审批卡。
- 计算图暂以「依赖缩进的列表」呈现，图形化视图放后续版本。

## 15. 请你重点确认

1. **影响类型只需要四类**（写文件 / 删除 / 执行命令 / 网络）够不够？删除目前实际由命令完成，所以「删除」严格说会落在 `exec` 里——要不要单独把「删除」作为节点 `effect` 展示、但仍按 `exec` 放行？
2. **同一时刻只允许一个 running 节点**（审计归属干净、但模型不能并行执行两个节点）。接受吗？还是允许并行、审计按影响类型归并？
3. **一个节点失败后可以直接重试**（不消耗、不重新批准）。你之前说「执行成功才消耗」，这条是它的直接推论——确认。
4. **审计留痕的展示位置**：节点行展开（推荐，随面板走）还是单独一个「执行记录」页？
